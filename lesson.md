# Git - система контроля версий

## Зачем нужен Git?

1. Хранит историю всех изменений в коде и позволяет откатываться к более ранней версии.
2. Позволяет задокументировать каждую строчку в коде - позволяет описать что мы сделали и для чего - благодаря истории коммитов.
3. Упростить возможность совместной работы над одним и тем же кодом - благодаря веткам.

## Установка и первоначальная настройка

1. **Установка Git на компьютер**  
   [https://git-scm.com/](https://git-scm.com/)

2. **Первичная настройка Git на компьютере**
   ```bash
   git config --global user.name "Pavel Bulygin"
   git config --global user.email "work@devbulygin.ru"
   git config --list
   ```

3. **Генерация SSH ключей**  
   [Документация GitHub](https://docs.github.com/ru/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent?platform=mac)

   ```bash
   ssh-keygen -t ed25519 -C "work@devbulygin.ru"
   ```

   **Просмотр SSH ключа:**
    - **Windows** - программа Git Bash:
      ```bash
      start ~/.ssh
      ```
    - **macOS/Linux** - терминал:
      ```bash
      open ~/.ssh
      ```

   Открывается окно проводника - в текстовом редакторе открываем файл с расширением `.pub`.

4. Открываем **Settings → SSH and GPG keys → New SSH key**.  
   Сохраняем название устройства, с которого сгенерировали ключ, вставляем сгенерированный ключ в настройки GitHub.

## Начало работы с Git

1. **Создание репозитория GitHub**  
   Переходим на страницу с репозиториями → выбираем **New**.  
   Заполняем имя репозитория (kebab-case), опционально описание.

2. **Клонирование репозитория**  
   `git init` - инициализация локального репозитория (в дальнейшем потребуется связывание его с GitHub, мы пошли более простым путем и склонировали репозиторий с GitHub).

   В настройках репозитория: **Code → Clone → SSH** и копируем команду.

3. Открываем в терминале папку, куда хотим склонировать репозиторий и пишем:
   ```bash
   git clone [скопированная_команда_из_GitHub]
   ```

4. Создаем файл `readme.md` (в появившемся окне "Add file to Git" отмечаем **Don't ask again** и закрываем окно - это графическая часть интерфейса Git).

## Базовые команды Git

1. **Текущий статус локального репозитория**
   ```bash
   git status
   ```

2. **Добавление файлов в индекс (staging area)**
   ```bash
   git add readme.md
   git add .
   ```
   `git add .` добавляет все неотслеживаемые изменения в индекс.

3. **Создание .gitignore**  
   Создаем файл `.gitignore` и пишем в него названия директорий и файлов, которые Git должен игнорировать:  
   `.idea`, `env` файлы, `build`.

4. **Очистка индекса**  
   Так как мы создали `.gitignore` уже после `git add .`, в индекс попало то, что нам не хотелось бы. Сбросим индекс:
   ```bash
   git reset
   ```
   *После этого проверяем статус - `git status`.*  
   Снова добавляем нужные файлы:
   ```bash
   git add .
   ```
   Удостоверяемся, что в индексе только `readme.md`.

5. **Создание коммита**
   ```bash
   git commit -m "feat: initial project structure"
   ```
   https://www.conventionalcommits.org - соглашение по коммитам
   В `readme.md` вносим заголовок **"Практика по Git"**, добавляем изменения в индекс.

6. **Просмотр истории коммитов**
   ```bash
   git log
   ```
   *Последний коммит всегда будет вверху.*

7. **Отправка коммитов в GitHub**
   ```bash
   git push
   ```

8. **Получение коммитов с сервера**  
   В интерфейсе GitHub добавляем новый файл `git-notes.md` и записываем, что сделали изменения на сервере.  
   Убеждаемся, что локально файл не появился.  
   Делаем изменения в `readme.md` и пушим → получаем ошибку "ветка отстает".  
   **Синхронизируем ветки:**
   ```bash
   git pull --rebase
   ```
   *Git просит выбрать стратегию - выбираем rebase.*

## Работа с ветками

Для удобной работы в команде в Git существует система веток.  
В каждой системе Git есть главная ветка: **GitHub - main**, **GitLab - master**. В ней хранится актуальный код.  
Разработчик создает ветку от основной, вносит изменения, после ревью ветка сливается обратно.

### Переключение веток

Создаем локальную ветку:
```bash
git branch add-developer-information
```

Проверяем текущую ветку:
```bash
git status
```
*Удостоверимся, что все еще на `main`.*

Переключаемся:
```bash
git checkout add-developer-information
```

Удостоверяемся, что на новой ветке.  
В `readme.md` пишем свое имя.

**Сценарий: срочное задание**  
Переключаемся на `main`:
```bash
git checkout main
```
В заголовке `readme.md` добавляем дату → `git add .` → коммит.

Пушим в `main`:
```bash
git push
```

Возвращаемся на ветку разработчика:
```bash
git checkout add-developer-information
```

Пушим изменения:
```bash
git push origin add-developer-information
```
*Указываем `origin`, чтобы пушить именно в нашу ветку, а не в `main`.*

### git stash

В `readme.md` добавляем "Java разработчик".  
Нужно срочно переключиться → **не коммитим, используем stash**:
```bash
git stash
```

После работы на другой ветке возвращаемся и восстанавливаем изменения:
```bash
git stash pop
```
Делаем коммит и пушим.

## Слияние веток - merge

Переключаемся на ветку, в которую сливаем:
```bash
git checkout main
```

Сливаем:
```bash
git merge add-developer-information
```

**Получаем конфликт** - убираем лишние строки, формируем итоговый вариант → `git add .` → коммит.

*В IDE видно, как формируются ветки при merge (создается merge-коммит).*

## Слияние веток - rebase

Создаем и переключаемся на новую ветку:
```bash
git checkout -b git-notes-updates
```

В `git-notes.md` делаем изменения → коммиты.

**Rebase на main:**
```bash
git rebase main
```

Переключаемся на `main`:
```bash
git checkout main
```

Сливаем без merge-коммита:
```bash
git merge git-notes-updates
```

**Разница merge vs rebase:**
- **Merge** - создает merge-коммит, сохраняет историю ветвления
- **Rebase** - "переписывает" историю, линейная история коммитов

## Откат изменений

1. Заходим на GitHub → выбираем нужный коммит → копируем хеш.
2. Выполняем:
   ```bash
   git revert [хеш_коммита]
   ```
3. Разрешаем конфликт:
   ```bash
   git add .
   git revert --continue
   git push
   ```
