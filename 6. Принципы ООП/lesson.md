
# Принципы ООП в Java

## 1. Инкапсуляция

### Что такое инкапсуляция

Инкапсуляция — это:

1. Объединение данных и методов работы с ними в одном классе.
2. Сокрытие внутренней реализации и защита состояния объекта.

Изначальное значение слова «инкапсуляция» в программировании — объединение данных и методов работы с этими данными в одной упаковке («капсуле»).

---

## Объединение данных и поведения

```java
public class Cat {

    private String name;
    private int age;
    private double weight;

    public void meow() {
        System.out.println("Мяу!");
    }
}
````

Класс содержит:

* состояние (поля)
* поведение (методы)

Это и есть инкапсуляция в базовом смысле.

---

## Сокрытие данных

Плохой вариант:

```java
public class Cat {
    public String name;
    public int age;
}
```

Можно сделать:

```java
Cat cat = new Cat();
cat.age = -100;
```

Это нарушает корректность состояния.

Правильный вариант:

```java
public class Cat {

    private String name;
    private int age;
    private double weight;

    public Cat(String name, int age, double weight) {
        setName(name);
        setAge(age);
        setWeight(weight);
    }

    public void setAge(int age) {
        if (age < 0) {
            throw new IllegalArgumentException("Возраст не может быть отрицательным");
        }
        this.age = age;
    }

    public int getAge() {
        return age;
    }

    // аналогично для остальных полей
}
```

Теперь объект всегда находится в корректном состоянии.

---

## Модификаторы доступа

| Модификатор | Доступ                |
| ----------- | --------------------- |
| `private`   | Только внутри класса  |
| `protected` | В пакете + наследники |
| `default`   | Только в пакете       |
| `public`    | Везде                 |

---

## Сокрытие реализации

Пользователь не должен знать, как реализован метод:

```java
public void feed(double foodWeight) {
    weight += foodWeight * 0.8; // внутренняя логика
}
```

Снаружи важен только контракт:

```java
cat.feed(0.2);
```

---

## Что дает инкапсуляция

* Контроль состояния
* Гарантии корректности
* Возможность менять реализацию без изменения интерфейса
* Снижение связанности

---

# 2. Наследование

Есть:

* **Animal** — общее для всех животных
* **Cat** и **Dog** — конкретные животные

У всех животных есть:

* `name`
* `age`

Но:

* у кота есть **любимая игрушка**
* у собаки есть **уровень дрессировки**

---

## 2. Родитель `Animal`

```java
public class Animal {

    protected String name;
    protected int age;

    public Animal(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```


* `Animal` — **родитель**
* Он содержит **только то, что есть у всех**
* Никаких “кошачьих” или “собачьих” деталей здесь быть не должно

---

## 3. Класс `Cat` — наследник со своим полем

```java
public class Cat extends Animal {

    private String favoriteToy;

    public Cat(String name, int age, String favoriteToy) {
        super(name, age);
        this.favoriteToy = favoriteToy;
    }
}
```

* `Cat extends Animal` → кот **наследует** имя и возраст
* `favoriteToy` — **уникальное поле кота**
* Это поле **не имеет смысла** для `Dog` → поэтому его нет в `Animal`

---

## 4. Класс `Dog` — наследник со своим полем

```java
public class Dog extends Animal {

    private int trainingLevel; // уровень дрессировки

    public Dog(String name, int age, int trainingLevel) {
        super(name, age);
        this.trainingLevel = trainingLevel;
    }
}
```

### Объяснение

* `trainingLevel` есть **только у собак**
* Кот не может иметь уровень дрессировки → значит поле не общее

---

## 5. Конструкторы и `super`

Важно подчеркнуть:

```java
super(name, age);
```

👉 означает:

> «Сначала создай **часть Animal**, потом добавь **часть Cat / Dog**»

Порядок создания объекта:

1. Конструктор `Animal`
2. Конструктор `Cat` или `Dog`

---

## 6. Проверка наследования на практике

```java
public class Main {
    public static void main(String[] args) {

        Cat cat = new Cat("Мурка", 3, "Мячик");
        Dog dog = new Dog("Бобик", 5, 7);

        System.out.println(cat.name); // доступно из Animal
        System.out.println(dog.age);  // доступно из Animal
    }
}
```

* `Cat` и `Dog` **автоматически получили** поля `name` и `age`
* Мы их **не объявляли повторно**
* Это и есть **наследование состояния**

---

## 7. Почему нельзя положить все поля в `Animal`

 Плохой вариант:

```java
public class Animal {
    String name;
    int age;
    String favoriteToy;
    int trainingLevel;
}
```

Почему плохо:

* У собаки нет любимой игрушки кота
* У кота нет уровня дрессировки
* Класс перестаёт быть логичным

👉 **Родитель должен быть максимально универсальным**

---

## Все классы наследуются от Object

В Java любой класс **неявно наследуется от `Object`**:

```java
public class Cat {
}
```

Фактически это:

```java
public class Cat extends Object {
}
```

---

## Что такое Object?

`Object` — корневой класс иерархии Java.

Он содержит базовые методы:

```java
public boolean equals(Object obj)
public int hashCode()
public String toString()
protected Object clone()
protected void finalize()
public final Class<?> getClass()
public final void wait()
public final void notify()
public final void notifyAll()
```

### Основные методы:

* `toString()` — строковое представление
* `equals()` — сравнение объектов
* `hashCode()` — хеш-код
* `getClass()` — получение типа во время выполнения

Пример переопределения:

```java
@Override
public String toString() {
    return "Cat{name='" + name + "', age=" + age + "}";
}
```

---


## Переопределение методов

```java
@Override
public void say() {
    System.out.println("Животное говорит привет");
}
```

`@Override`:

* помогает избежать ошибок
* гарантирует, что метод действительно переопределяется

---

## Что нельзя переопределить

* `final`
* `private`
* `static`

# 3. Полиморфизм

## 3. Полиморфизм

**Полиморфизм** — это способность объектов с одинаковым базовым типом вести себя по-разному.
Проще говоря:

> Один тип (`Cat`) — много форм поведения.

Полиморфизм позволяет работать с объектами через **общий родительский тип**, не зная их конкретного класса.

---

# 3.1. Полиморфизм времени выполнения (Runtime Polymorphism)

Это основной вид полиморфизма в Java.
Он реализуется через:

* наследование
* переопределение методов (overriding)
* динамическое связывание (dynamic dispatch)

---

### Базовый класс

```java
class Animal {
    void sayHello() {
        System.out.println("Животное говорит Привет");
    }
}
```

---

### Дочерние классы

```java
class Cat extends Animal {
    @Override
    void sayHello() {
        System.out.println("Кот говорит Привет");
    }
}
```

```java
class Dog extends Animal {
    @Override
    void sayHello() {
        System.out.println("Собака говорит Привет");
    }
}
```

---

### Использование полиморфизма

```java
Animal firstAnimal = new Cat();
Animal secondAnimal = new Dog();

firstAnimal.sayHello(); // Кот говорит Привет
firstAnimal.sayHello(); // Собака говорит Привет
```

---

### Что здесь происходит?

* Тип переменной: `Animal`
* Реальный объект: `Cat` или `Dog`
* JVM во время выполнения определяет, какой метод вызвать

Это называется **динамическое связывание**.

Метод выбирается по **реальному объекту**, а не по типу ссылки.

---

# 3.2. Как это работает внутри

Когда метод не `static`, не `private`, не `final`, он является **виртуальным**.

JVM:

1. Смотрит на реальный тип объекта
2. Ищет переопределённый метод
3. Вызывает его

Это и есть механизм runtime polymorphism.

---

# 3.3. Важно: поля не полиморфны

```java
class Animal {
    String type = "Animal";
}

class Cat extends Animal {
    String type = "Cat";
}

Cat cat = new HomeCat();
System.out.println(cat.type); // Cat
```

Поля определяются типом ссылки (`Animal`),
методы — типом объекта (`Cat`).

---

# 3.4. Правила переопределения (Overriding)

Чтобы метод считался переопределённым:

* имя совпадает
* параметры совпадают
* возвращаемый тип совпадает (или более узкий)
* уровень доступа нельзя уменьшать
* нельзя переопределить `final` метод
* `static` методы не переопределяются (они скрываются)

---

### Пример ошибки

```java
class Cat {
    final void sleep() {}
}

class HomeCat extends Cat {
    void sleep() {} // ошибка — нельзя переопределить final
}
```

---

# 3.5. Static методы — не полиморфизм

```java
class Animal {
    static void info() {
        System.out.println("Animal");
    }
}

class Cat extends Animal {
    static void info() {
        System.out.println("HoCatmeCat");
    }
}

Animal animal = new Cat();
animal.info(); // Animal
```

Static методы выбираются по типу ссылки.

Это не runtime polymorphism.

---

# 3.6. Upcasting и Downcasting

### Upcasting — безопасно

```java
Animal animal = new Cat();
```

Ссылка родителя указывает на дочерний объект.

---

### Downcasting — потенциально опасно

```java
Animal animal = new Cat();
Cat cat = (Cat) animal; // безопасно
```

Но:

```java
Animal animal = new Dog();
Cat cat = (Cat) animal; // ClassCastException
```

Проверка:

```java
if (animal instanceof Cat) {
    Cat cat = (Cat) animal;
}
```

---

# 3.7. Зачем нужен полиморфизм

Он позволяет писать расширяемый код.

```java
void makeAnimaltSpeak(Animal animal) {
    animal.sayHello();
}
```

Метод не знает:

* `Cat`
* `Dog`
* любой другой наследник

Но работает с любым.

Добавим новый класс:

```java
class Chicken extends Cat {
    @Override
    void sayHello() {
        System.out.println("Курица говорит Привет");
    }
}
```

Код `makeCatSpeak` менять не нужно.

Это основа:

* гибкой архитектуры
* расширяемости
* принципа подстановки Лисков (LSP)

---

# 3.9. Главная идея

Полиморфизм — это:

* один общий тип
* много различных реализаций
* выбор поведения во время выполнения

Он работает только для методов и основан на наследовании.

## 4. Абстракция

**Абстракция** — это принцип ООП, при котором мы скрываем детали реализации и оставляем только существенные характеристики объекта.

Проще:

> Мы описываем, **что умеет делать `Cat`**, но не обязательно говорим, **как именно это реализовано**.

Абстракция позволяет работать с общим понятием, не вникая в конкретные детали.

---

# 4.1. Зачем нужна абстракция

Представим, что у нас есть разные виды животных `Animal`:

* Кот
* Собака
* Курица

У всех есть общее поведение:

* здороваться


Но реализация может отличаться.

Абстракция позволяет:

* задать общий контракт
* скрыть конкретную реализацию
* заставить наследников реализовать обязательные методы

---

# 4.2. Абстрактный класс

Абстрактный класс — это класс, который:

* объявляется с ключевым словом `abstract`
* **нельзя создать напрямую**
* может содержать абстрактные методы
* может содержать обычные методы
* может содержать поля
* может иметь конструктор

---

### Пример

```java
abstract class Animal {
    public sayHello();
}
```

---

### Что здесь важно

1. Метод `say Hellp()` — абстрактный
   → у него нет реализации
   → каждый наследник обязан его реализовать


2. Есть поле `name`
   → у всех животных есть имя

---

# 4.3. Реализация абстрактного класса

```java
class Cat extends Animal {

    Cat(String name) {
        super(name);
    }

    @Override
    void sayHello() {
        System.out.println("Кошка говорит привет");
    }
}
```

---

### Использование

```java
Animal animal = new Cat("Barsik");
cat.sayHello();
```

Мы работаем через абстракцию `Animal`.

---

# 4.4. Почему нельзя создать абстрактный класс

```java
Animal animal = new Animal("Test"); // ошибка
```

Потому что:

* у него есть абстрактный метод
* он не полностью реализован
* это шаблон, а не конкретный объект

---

# 4.5. Когда использовать абстрактный класс

Используем, когда:

* есть общее состояние (поля)
* есть общая логика
* нужно частично реализованное поведение
* нужно заставить наследников реализовать обязательные методы

# 4.6. Интерфейс как форма абстракции (расширенная версия)

Интерфейс — это способ задать **контракт поведения**.

Он отвечает на вопрос:

> Что объект обязан уметь делать?

А не:
> Как именно это реализовано?

---

## 4.6.1. Базовый синтаксис

```java
interface Flyable {
    void fly();
}
````

Все методы интерфейса по умолчанию являются:

* `public`
* `abstract`

То есть запись:

```java
void fly();
```

эквивалентна:

```java
public abstract void fly();
```

---

## 4.6.2. Переменные в интерфейсе

Все поля интерфейса автоматически имеют модификаторы:

* `public`
* `static`
* `final`

Даже если это явно не указано.

Пример:

```java
interface Constants {
    int MAX_SPEED = 120;
}
```

На самом деле это:

```java
public static final int MAX_SPEED = 120;
```

### Что это означает?

* `public` — доступно везде
* `static` — принадлежит интерфейсу, а не объекту
* `final` — это константа (её нельзя изменить)

Попытка изменить значение:

```java
Constants.MAX_SPEED = 200; // ошибка компиляции
```

---

### Важно

Интерфейс **не хранит состояние объекта**.

Он может содержать только константы.

Так писать нельзя:

```java
interface Test {
    int count; // ошибка — поле должно быть инициализировано
}
```

---

## 4.6.3. Реализация интерфейса

```java
class Bird implements Flyable {

    @Override
    public void fly() {
        System.out.println("Птица летит");
    }
}
```

Обратите внимание:

Метод обязан быть `public`.

Если написать:

```java
void fly() { }
```

→ будет ошибка компиляции.

Почему?

Потому что метод в интерфейсе `public`, и уменьшать область видимости нельзя.

---

# 4.6.4. Default-методы (методы с реализацией)

Начиная с Java 8, интерфейсы могут содержать `default` методы — методы с реализацией.

```java
interface Flyable {

    void fly();

    default void land() {
        System.out.println("Объект приземляется");
    }
}
```

Теперь класс может:

* реализовать `fly()`
* использовать готовую реализацию `land()`
* либо переопределить `land()`

---

### Пример

```java
class Bird implements Flyable {

    @Override
    public void fly() {
        System.out.println("Птица летит");
    }
}
```

Метод `land()` уже доступен без переопределения.

---

## Зачем нужны default-методы?

1. Для расширения интерфейсов без поломки старого кода
2. Для добавления общей логики
3. Для эволюции API

---

## 4.6.5. static-методы в интерфейсе

Интерфейс может содержать `static` методы:

```java
interface MathUtil {

    static int square(int x) {
        return x * x;
    }
}
```

Вызываются так:

```java
MathUtil.square(5);
```

Важно:

* `static` методы **не наследуются**
* их нельзя вызвать через объект

---

# 4.6.6. Области видимости (важные нюансы)

## В интерфейсе:

* Все методы → `public`
* Все поля → `public static final`
* Конструкторов нет
* Поля экземпляра запрещены

---

## В абстрактном классе:

Можно использовать любые модификаторы:

* `private`
* `protected`
* `public`
* package-private

Пример:

```java
abstract class Animal {

    private String secret;      // доступен только внутри класса
    protected String name;      // доступен наследникам
    public int age;             // доступен везде

    protected abstract void makeSound();
}
```

---

## Наследование области видимости

### Правило:

Нельзя уменьшать область видимости при переопределении метода.

Пример:

```java
abstract class Animal {
    protected abstract void makeSound();
}
```

Наследник:

```java
class Cat extends Animal {

    @Override
    public void makeSound() {  // можно расширить (protected → public)
        System.out.println("Мяу");
    }
}
```

Но так нельзя:

```java
@Override
private void makeSound() { } // ошибка
```

---

## Интерфейс и модификаторы

До Java 9 нельзя было объявлять `private` методы в интерфейсе.

Начиная с Java 9 разрешены `private` методы,
но только для внутренней служебной логики `default` методов.

---

# 4.6.7. Множественная реализация интерфейсов

Класс может реализовать несколько интерфейсов:

```java
class Duck implements Flyable, Swimmable {
    ...
}
```

Это возможно потому что:

* интерфейсы не хранят состояние
* нет проблемы множественного наследования полей

---

## Конфликт default-методов

Если два интерфейса содержат одинаковый `default` метод:

```java
interface A {
    default void test() { }
}

interface B {
    default void test() { }
}
```

Класс обязан переопределить метод:

```java
class C implements A, B {

    @Override
    public void test() {
        A.super.test(); // можно явно вызвать реализацию
    }
}
```

---

# 4.6.8. Абстрактный класс vs Интерфейс (расширенная таблица)

| Критерий        | Абстрактный класс        | Интерфейс                     |
| --------------- | ------------------------ | ----------------------------- |
| Поля            | Можно любые              | Только `public static final`  |
| Конструктор     | Есть                     | Нет                           |
| Методы          | Любые                    | `public`, `default`, `static` |
| Наследование    | Только один класс        | Можно реализовать несколько   |
| Состояние       | Да                       | Нет                           |
| Когда применять | Общая логика + состояние | Контракт поведения            |

# 4.6.9. Когда что использовать

### Использовать интерфейс, если:

* нужен контракт
* нет общего состояния
* нужна множественная реализация
* архитектура строится вокруг поведения

### Использовать абстрактный класс, если:

* есть общее состояние
* есть частичная реализация
* нужна общая логика
* требуется защита данных через `protected` / `private`
